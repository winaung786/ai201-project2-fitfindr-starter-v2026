# FitFindr acceptance criteria

These targets were set before implementation testing. A try means one fresh call to `run_agent` with the named input; record the returned session and tool call log each time. For model behavior, disable any response cache during the five tries.

1. Given `vintage graphic tee under $30, size M` with the example wardrobe, the agent completes `search_listings`, `suggest_outfit`, and `create_fit_card` in that order and returns a nonempty fit card in at least **4 of 5** tries.
   **Why this target:** The three-step flow is the main experience. One transient model failure is tolerable if the remaining tries work, but a lower target would hide a recurring failure.

2. Given `designer ballgown size XXS under $5` with the example wardrobe, the agent stops after `search_listings`, leaves `selected_item`, `outfit_suggestion`, and `fit_card` as `None`, and says to change a keyword, size, or price in **5 of 5** tries.
   **Why this target:** An empty result is deterministic for the supplied data, so every run should stop and offer a useful next action.

3. Run the query in criterion 1 with the example wardrobe five times. For this state check, replace `agent.suggest_outfit` and `agent.create_fit_card` with recording functions that capture the `new_item["id"]` each actually receives and return nonempty text. In **5 of 5** runs, both captured IDs must equal `session["selected_item"]["id"]`, and `session["selected_item"]` must equal `session["search_results"][0]`. A missing call or item counts as a failure.
   **Why this target:** I chose a **5 out of 5** target because passing the selected item from search to `suggest_outfit` and `create_fit_card` should be deterministic, unlike model-generated text. Recording the item IDs actually received by the tools verifies the real transfer, not just what the agent says happened in its log.

4. Across **5** runs of the query in criterion 1 with the example wardrobe and the response cache off, at least **4** fit cards must be 1–4 sentences, contain the selected item's exact `title`, its price formatted to two decimal places (for example, `$18.00`), and its `platform` name. A card must not claim the user owns a specific clothing item unless that item's name appears in `wardrobe["items"]`. A missing fit card fails that try.
   **Why this target:** I chose a **4 out of 5** target because the fit card is generated by a language model, so its wording can vary between runs. The exact title, correctly formatted price, platform, and ownership claims should still be reliable; allowing one failure accounts for occasional model variation without accepting a pattern of inaccurate cards.

5. Across **5** runs of `vintage graphic tee under $30, size M` with `get_empty_wardrobe()` and the response cache off, at least **4** sessions must have no error and a nonempty `outfit_suggestion` that names the selected item's exact `title` and suggests at least one other clothing or shoe type (for example, jeans or sneakers). The suggestion must not say the user owns a specific piece. A missing item or suggestion fails that try.
   **Why this target:** I chose a **4 out of 5** target because FitFindr should still name the selected item and suggest a clothing or shoe pairing when the user has no saved wardrobe items, without claiming the user owns specific clothing. One imperfect model response is acceptable, but repeated failures would make this user path unreliable.

## Unit 9 Capstone — student-supplied acceptance criteria

These **five numbered criteria were supplied by the student** and recorded in Git before the new Unit 9 student-criteria test results. Their specified text targets, including the en dash in "Y2K Baby Tee – Butterfly Print", have been **preserved** and are scored literally; the actual listing's title contains an em dash (—), which may cause a genuine miss. The earlier AI-assisted rehearsal and its results are preserved separately, not used as this student's results.

1. **Happy-path HTTP telemetry and correlation header:** Given `POST /ask` with `{"query": "vintage graphic tee under $30, size M"}` (omitting `wardrobe` so `serve.py` uses `get_example_wardrobe()`), the server returns HTTP `200` with a 12-character hex `X-FitFindr-Run-ID` response header and appends one JSONL record to `FITFINDR_LOG_PATH` whose `run_id` matches the header, `http_status` is `200`, `duration_ms` is greater than `0`, `output.selected_item_id` is `"lst_002"`, `output.error` is `null`, and `output.fit_card` contains `"Y2K Baby Tee – Butterfly Print"`, `"$18.00"`, and `"depop"`, in **3 of 3** trials. **Why this target:** I chose a **3 of 3** target because the HTTP wrapper, `X-FitFindr-Run-ID` header injection, MCP search ranking for `lst_002` in `data/listings.json`, and JSONL serialization in `capstone_logging.py` are deterministic operational plumbing where any mismatch would break request tracing.

2. **Bounded size-retry and empty-search failure-path telemetry:** Given `POST /ask` with `{"query": "designer ballgown size XXS under $5"}`, the server returns HTTP `200` where `selected_item`, `outfit_suggestion`, and `fit_card` are `null`, `tool_calls` records two `search_listings` calls (initial search plus one retry with `retry: true` and `dropped_constraint: "size XXS"`), and the appended JSONL record captures `output.selected_item_id: null`, `output.fit_card: null`, `output.retry_notice: "No matches in size XXS; retried once without the size filter."`, and `output.error` starting with `"No listings match that request, even after dropping the size filter"`, in **3 of 3** trials. **Why this target:** I chose a **3 of 3** target because the empty-search and bounded size-retry branch in `agent.py` is a deterministic failure path against `data/listings.json`, so every run must log both the retry notice and the stopping reason.

3. **Malformed and non-string JSON payload rejection (HTTP 400 failure path):** In each trial, sending three invalid `POST /ask` payloads in sequence — an empty object `{}`, a non-object JSON array `["vintage graphic tee under $30"]`, and a non-string query `{"query": 123}` — returns HTTP `400` (never HTTP `500`) with `"Send JSON with a 'query' field, e.g. {\"query\": \"vintage graphic tee under $30\"}"`, and each appends a JSONL record with `http_status: 400`, `model_calls: 0`, `duration_ms` less than `50`, and `output.error` containing the `400` validation message, in **3 of 3** trials. **Why this target:** I chose a **3 of 3** target because input validation in `serve.py::ask` runs synchronously before acquiring `_one_at_a_time` or invoking the agent, so malformed requests should deterministically return `400 Bad Request` rather than raising an `AttributeError` masked as `500 Internal Server Error`.

4. **Secret/wardrobe privacy redaction and temporary MCP metrics file cleanup:** Given `POST /ask` with `{"query": "vintage graphic tee under $30, size XL"}` and `GEMINI_API_KEY="test_secret_key_DO_NOT_LOG_999"` set in the environment, the appended JSONL record never contains the `GEMINI_API_KEY` value or any raw wardrobe item names (such as `"Baggy straight-leg jeans, dark wash"`), records `output.selected_item_id: "lst_006"` and `output.retry_notice: "No matches in size XL; retried once without the size filter."`, and leaves zero `fitfindr-capstone-*` temporary directories in the system temp directory after the request finishes, in **3 of 3** trials. **Why this target:** I chose a **3 of 3** target because credential redaction, wardrobe privacy, and temporary file cleanup in `capstone_logging.py::_measure_one` are strict security and resource-hygiene invariants where even a single leak is unacceptable.

5. **Explicit empty-wardrobe HTTP styling and zero-item telemetry:** Given `POST /ask` with `{"query": "vintage graphic tee under $30, size M", "wardrobe": {"items": []}}`, the server returns HTTP `200` with `error: null`, a nonempty `outfit_suggestion` stating no wardrobe is saved and pairing `"Y2K Baby Tee – Butterfly Print"` with general clothing/shoe types without claiming ownership, and appends a JSONL record with `input.wardrobe_item_count: 0`, `output.selected_item_id: "lst_002"`, and a nonempty `output.fit_card` mentioning `"$18.00"`, in **3 of 3** trials. **Why this target:** I chose a **3 of 3** target because passing an explicit empty wardrobe over HTTP verifies both the `input.wardrobe_item_count: 0` telemetry summary and the deterministic fallback/validation guard in `tools.py::suggest_outfit`.
